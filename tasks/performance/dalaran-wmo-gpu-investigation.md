# Даларан: причина GPU-затрат WMO — 2026-10-21

Главный подтверждённый расход в изолированном WMO Даларана — чтение и восстановление RT-освещения в пиксельном шейдере. Отключение только этого чтения сократило проход WMO с **7.62 до 2.57 мс**. Сам RT compute оставался включённым. Это диагностическое отключение, не исправление с сохранением качества.

## Контролируемая диагностика

Один зафиксированный scene_render и набор shader assets; AMD Radeon RX 7700 XT, driver 2.0.395, Vulkan 1.4.349, validation выключена. Полный ND_DALARAN.WMO в своей мировой позиции, камера/FOV/час первого кадра сохранённой записи Даларана, 2560×1369. Нет terrain, персонажей, doodads, воды и фонового streaming. RT=3, radius=300, MSAA=1, FXAA включён; POM medium/32, shadow quality 2 — defaults scene_render, а не все настройки записанного клиента.

По 240 кадров на режим, первые 10 не входят в отчёт. FIFO/VSync ограничивает FPS примерно 60; сравниваем **GPU timestamp WMO**, не FPS. Один прогон на режим, частоты GPU не зафиксированы. Разницы нельзя складывать как независимые выигрыши.

| Диагностический режим | WMO GPU mean, мс | p95, мс | Изменение mean |
|---|---:|---:|---:|
| Исходный шейдер | 7.62 | 11.74 | — |
| Только frustum-culling групп | 7.29 | 8.16 | −4.3% |
| Без POM | 7.04 | 8.10 | −7.6% |
| Без широких recovery-колец RT, локальный lookup сохранён | 4.28 | 4.65 | −43.8% |
| Без RT lookup в WMO, сам RT compute сохранён | 2.57 | 3.01 | −66.3% |
| Принудительный early_fragment_tests, только диагностика | 6.46 | 7.02 | −15.2% |
| Простой текстурный шейдер с alpha-test и distance cutoff | 0.50 | 0.64 | −93.4% |

Режим early_fragment_tests меняет запись depth при discard и потому **не годится как готовое исправление** alpha-cutout материалов. Простой шейдер также меняет картинку и отключает POM: он показывает нижнюю оценку стоимости этой геометрии с дешёвым shading, а не равнозначное качество. Скриншот без RT recovery отличается от исходного; движение камеры и раскрытие поверхностей здесь не проверялись.

Монитор не зарегистрировал конкурирующие процессы в принятых прогонах. Первый no-recovery исключён: параллельно запустился scene_render из aerial-march checkout. Его лог/PNG сохранены с префиксом excluded-competing; чистый повтор выполнен после освобождения GPU.

## Где расходуется время

Уточнение причины после вопроса пользователя: текущий forward renderer сначала рисует мир и получает depth, затем запускает RT по этому depth. WMO текущего кадра поэтому читает результат предыдущего кадра (`include/rendering/rt_lighting.hpp:22`, `Renderer::recordRtLighting` после world pass). Широкий recovery компенсирует отсутствие receiver в старом экранном буфере при движении/раскрытии поверхности; это не обязательная часть трассировки лучей. До оптимизации самого поиска следует оценить порядок **текущая visibility/depth → текущий RT → shading**, отдельно оставив контролируемый half-resolution resolve и history для denoising. Стоимость prepass/G-buffer, синхронизации, alpha-cutout и отдельного transparent path ещё не измерена; ускорение такого изменения не установлено.

`assets/shaders/wmo.frag.glsl:333` вызывает `rtLightAt` при отрисовке поверхности. В `assets/shaders/rt_lighting.glsli:118` сначала проверяются четыре texel bilinear footprint. При несовпадении глубины/нормали выполняется gather 3×3, затем при недостаточной уверенности ещё четыре кольца radius 2/4/8/16. Это до 41 gather-кандидата сверх первоначальной проверки; кандидат читает light/geometry, при подходящем весе — GI, вычисляет веса и восстанавливает normal. Широкие кольца сами объясняют крупную часть затрат по диагностическому отключению.

Это происходит при shading фрагментов, а не один раз на модель. Большая площадь WMO и повторное shading перекрывающихся поверхностей могут усиливать расход; количество fragment invocations и доля каждого пути аппаратными счётчиками не измерялись. Поэтому конкретный коэффициент overdraw не установлен.

Правильная следующая работа — уменьшать стоимость RT reconstruction/recovery при сохранении проверки receiver depth/normal и поведения на disocclusion, исследовать перенос тяжёлого recovery в отдельное разрешение освещения и избегать его повторения для скрытых слоёв. Простое удаление колец может вернуть яркие края на открывающихся поверхностях. Нужны движущиеся камера/персонажи, углы стен и тонкая геометрия при проверке исправления. Общий shader используется и другими типами объектов.

## Второй подтверждённый дефект: WMO не отсеивает группы по frustum

`src/rendering/wmo_renderer.cpp:1117` строит frustum, но после portal/distance проверок сразу добавляет группы в draw list. Извне здания portal traversal часто отключён; функция `isGroupVisible` вообще не вызывается. В фиксированном ракурсе из 91 группы 10 целиком вне frustum: **116 из 1619 draw calls**, 17,394 из 419,562 треугольников. Их исключение дало полностью идентичный PNG (SHA256 совпадает). Это корректный кандидат на оптимизацию, но не главный источник GPU-времени в данном ракурсе. В полном мире со множеством WMO доля может отличаться.

Нельзя просто добавить проверку в общий cullView: `extract:1096` сейчас строит reflection list с обычной камерой. Для корректного frustum-culling отражений нужен frustum отражённой камеры либо консервативный список; shadow/RT caster selection должны сохранять свои объёмы. Использовать следует корректные cached worldGroupBounds, а не старый неиспользуемый helper, который трансформирует только min/max AABB и неверен для повёрнутого здания.

Объединение материалов здесь даёт 1578 material batches при 1619 draws: дополнительное объединение диапазонов внутри уже существующих групп в этой сцене ограничено примерно 2.5% draw calls. Оба основных pipeline также используют CULL_MODE_NONE; отдельный вклад отсутствующего backface-culling не измерялся, и односторонние материалы нужно отличать от F_UNCULLED с учётом mirrored reflection.

## Артефакты и состояние

- `tasks/performance/dalaran-wmo-gpu-investigation.json`: settings, GPU distributions всех проходов, counters, hashes.
- `build-dev/scratch/wmo-gpu-investigation/`: fixed scene, frozen executable/assets, scripts, diagnostic shaders, logs и PNG каждого режима; baseline PNG равен frustum PNG побайтно.
- Исходная WMO source до/после временного probe совпадает побайтно; ранние незакоммиченные RT-изменения сохранены. Обычный scene_render успешно пересобран после удаления probe. Shader variants не устанавливались в общий build-dev/bin; общий WMO SPIR-V совпадает с исходным побайтно.
- Полный игровой replay повторно не запускался; его прежние **5.04 мс WMO** нельзя напрямую сравнивать с **7.62 мс** этой изолированной сцены. Найдена причина, готовый игровой фикс и прирост FPS пока не заявляются.
